# Error Journal — Kibah Asesores

## 1. View con columnas inventadas (M1)
- **Error:** El SQL de 001-foundation.sql usó columnas que no existen en base_kibah ("Nombre", "Tipo", "Precio")
- **Causa:** El prompt decía "genera el SQL del Master Doc" pero Claude Code no tiene acceso al Master Doc
- **Fix:** Se creó SQL corregido con columnas reales ("Nombre Desarrollador", "Precio por unidad", etc.)
- **Regla:** SIEMPRE verificar columnas reales leyendo la tabla en Supabase o el archivo SQL existente. NUNCA inventar nombres de columnas.

## 2. Carga de 2,600 propiedades sin paginación (M2)
- **Error:** La página se trabó y tumbó la computadora del usuario
- **Causa:** Se cargaron todas las propiedades de golpe sin respetar el límite de paginación
- **Fix:** Forzar LIMIT 20 por default, máximo 50 por request
- **Regla:** SIEMPRE paginar. NUNCA cargar más de 50 registros en una sola request. Default = 20.

## 3. Zod v4 API differences (M3)
- **Error:** Build failed because `z.enum()` second param uses `{ message: '...' }` not `{ errorMap: () => ({}) }`, and `z.number()` uses `{ error: '...' }` not `{ invalid_type_error: '...' }`. Also `ZodError.errors` doesn't exist — it's `ZodError.issues`.
- **Causa:** Project uses Zod v4 which has a simplified API compared to v3 docs.
- **Fix:** Changed to `z.enum(values, { message })`, `z.number({ error })`, and `err.issues`.
- **Regla:** This project uses Zod v4. Use `{ message }` for enums, `{ error }` for number/string, and `.issues` not `.errors` on ZodError.

## 4. Supabase JS client doesn't need SQL-escaped quotes in column names (M3)
- **Error:** `Could not find '% Comisión' column of 'base_kibah' in the schema cache` — insert/update failed.
- **Causa:** COLUMN_MAP had column names wrapped in escaped double quotes (`'"Nombre Kibah"'`). Supabase JS client handles quoting automatically — the object keys should be plain strings (`'Nombre Kibah'`).
- **Fix:** Removed all escaped double quotes from COLUMN_MAP values.
- **Regla:** When using Supabase JS `.insert()` / `.update()`, column names go as plain strings WITHOUT SQL quotes. The client handles quoting internally.

## 5. Campos numéricos no deben usar .int() si aceptan decimales (M3)
- **Error:** num_banos rechazaba 2.5 (medio baño) porque tenía `.int()` en el schema Zod.
- **Causa:** Se asumió que baños/recámaras/estacionamiento eran siempre enteros.
- **Fix:** Removido `.int()` de num_banos, num_recamaras, estacionamiento en el schema Zod.
- **Regla:** Solo usar `.int()` cuando el campo sea ESTRICTAMENTE entero. Baños/recámaras/estacionamiento pueden ser decimales (2.5 baños = medio baño).
## 6. Migración a proyecto Supabase de brika — propiedades ahora lee inventario_industrial
- **Error:** La app buscaba `propiedades_view`/`base_kibah` (esquema Kibah) en el proyecto Supabase nuevo de brika, que no tiene ese esquema; todo el módulo de propiedades daba 500.
- **Causa:** El código es un fork del CRM Kibah; el proyecto nuevo (`pmnxevxmaadtksoqifdo`) tiene los datos en `inventario_industrial` (naves/lotes industriales, mismo proyecto que usa el Laravel de brika).
- **Fix:** Se creó `src/lib/utils/inventario.ts` (mapa clave-frontend → columna real + mapper de filas). Las rutas GET `/api/properties` y `/api/properties/filter-options` y el DAL de lectura consultan `inventario_industrial` con el cliente admin (la tabla tiene RLS activado SIN políticas — la administra Laravel — así que el cliente de usuario vería 0 filas; las rutas verifican sesión antes de leer). Las escrituras (create/update/delete) siguen apuntando a `base_kibah` y NO funcionan aún.
- **Regla:** En este proyecto, toda lectura de inventario va vía `KEY_TO_COLUMN`/`mapInventarioRow` de `lib/utils/inventario.ts`. No crear tablas del esquema Kibah en la base de brika. Cambios de BD solo los aplica el usuario pegando SQL en el dashboard.

## 9. Textos con charSpace desalineados en jsPDF (Ficha Técnica BRIKA)
- **Error:** Al generar la ficha técnica, los textos con letter-spacing (`charSpace`) alineados a la derecha se desbordaban del margen y salían cortados en el borde de la página (ej. "LOTE INDUSTRIAL · APASEO EL GRAN"); los centrados quedaban corridos. Además `fmtMoney` con `maximumFractionDigits: 0` mostraba "$2 / m²" en vez de "$2.20 / m²" para precios por m².
- **Causa:** jsPDF calcula `align: 'right'/'center'` con `getTextWidth()`, que NO incluye el espacio extra de `charSpace` (~`charSpace × (chars-1)` mm adicionales). Y los precios por m² sí requieren centavos.
- **Fix:** Helpers `spacedTextRight`/`spacedTextCenter` en `src/components/pdf/ficha/draw.ts` que suman el charSpace al ancho y alinean a mano; `fmtMoneyDec` en `theme.ts` para montos por m². Verificado renderizando el PDF y revisándolo visualmente.
- **Regla:** En jsPDF, NUNCA combinar `charSpace` con `align: 'right'` o `'center'` — usar los helpers de `ficha/draw.ts`. Otros glifos que NO existen en las fuentes estándar (WinAnsi) de jsPDF: ✓ y ● — dibujarlos con líneas/círculos (ver `drawCheck`/`drawBullet`). Los PDFs se pueden verificar visualmente compilando el módulo con tsc a CommonJS y corriéndolo en Node (jsPDF funciona en Node con imágenes como dataURL).

## 11. Hydration error en /dashboard/pdf + imágenes de ficha siempre vacías
- **Error:** "Hydration failed because the initial UI does not match what was rendered on the server" al abrir el módulo de PDF con una selección guardada. Además la ficha nunca traía foto de portada.
- **Causa:** (1) `usePdfSelection` inicializaba el estado leyendo `sessionStorage` en el primer render — el SSR renderiza 0 seleccionadas y el cliente renderiza N → mismatch. (2) `/api/pdf/images` consultaba `desarrollos_view` (esquema Kibah, inexistente en la BD de brika) → mapa de imágenes siempre `{}`. Los links reales de `inventario_industrial.links_imagenes_carpetas_drive` son CARPETAS de Google Drive privadas (devuelven 401; además son `/drive/u/2/…`, atadas a la cuenta del usuario) — no se pueden renderizar sin OAuth de Drive.
- **Fix:** (1) El hook arranca vacío y se hidrata en `useEffect` (con flag `hydrated` para no pisar el storage con `[]` antes de cargar). (2) `/api/pdf/images` ahora lee `inventario_industrial` (`getInventarioImagesByParques` en `lib/dal/properties.ts`), usando el link solo si es URL directa a imagen (jpg/png/webp). (3) El builder permite adjuntar manualmente la foto de portada por propiedad (`coverMap` por id, dataURL en memoria, prioridad sobre la BD) — se incrusta al generar, sin tocar la BD.
- **Regla:** En hooks de cliente, NUNCA leer `localStorage`/`sessionStorage` en el inicializador de `useState` de componentes que se renderizan en SSR — siempre hidratar en `useEffect`. Los links de Drive del inventario son carpetas privadas: no asumir que se pueden mostrar; si se quiere portada automática, se necesita integración con la API de Drive (OAuth con scope drive.readonly) o una columna con URL directa de imagen.

## 12. Fuente real de imágenes de propiedades: propiedad_image_sets + bucket Imagenes
- **Error:** (Sigue de #11) La ficha no traía foto automática; el intento con `links_imagenes_carpetas_drive` no era viable (carpetas privadas de Drive).
- **Causa:** La fuente real está en Supabase: la tabla `propiedad_image_sets` (`propiedad_id` uuid → `image_set_id` int) liga cada propiedad con una carpeta del bucket **público** `Imagenes` (`{image_set_id}/1.jpg, 2.jpg, ...`). 293 filas (cobertura total del inventario). Se descubrió listando el esquema vía OpenAPI de PostgREST (`GET /rest/v1/` con service role) y `storage.listBuckets()`.
- **Fix:** `getInventarioImagesByIds` en `lib/dal/properties.ts`: ids → sets → primera imagen del set (prioriza archivos `portada|fachada|cover`, luego orden natural) → URL pública por el endpoint de **transformación** (`/render/image/public/...?width=1600&quality=80` — los originales pesan >10MB; el proyecto tiene transformaciones habilitadas y hasta convierte webp→jpeg). `/api/pdf/images` ahora recibe `{ ids }` (antes `{ nombres }`) y devuelve el mapa keyed por id de propiedad; PdfBuilder/PdfPreview/generateFichaPdf indexan por `p.id`. La portada manual del builder (#11) sigue teniendo prioridad.
- **Regla:** Las imágenes de propiedades brika viven en el bucket `Imagenes` vía `propiedad_image_sets` — NO en Drive ni en `desarrollos_view`. Para servir imágenes del bucket usar el endpoint de transformación con `width`, nunca el original. `Property.id` es uuid (string) aunque el type legacy diga number — como clave de objeto funciona, pero no asumir numérico.

## 17. Filtros de Propiedades: opciones duplicadas por mayúsculas/acentos ("Colon" y "Colón")

Para armar una ficha con varias propiedades había que paginar a ciegas; la búsqueda se sentía rota (resultados parciales, orden por fecha).
- **Causa:** Componente heredado del fork pensado para 2,600 filas residenciales (regla #2: nunca más de 50 por request). El inventario de brika tiene 443 filas y el selector solo necesita 12 columnas para listar.
- **Fix:** `getInventarioList()` en `lib/dal/properties.ts` (versión ligera `InventarioListItem` en `types/inventario.ts`, bloques de 1000, orden parque + unidad numérica) servido por `GET /api/pdf/properties` (`pdf.view`) y reutilizado por `/api/carta-propuesta/properties`. `PdfPropertySelector` carga todo una vez y busca en el cliente sin acentos/mayúsculas y por varias palabras ("acupark 14"); al marcar una propiedad pide la ficha completa a `GET /api/properties/[id]` (nuevo handler GET, `propiedades.view|pdf.view|carta_propuesta.view`) porque la ficha necesita las ~35 columnas. `precioListado()` en `lib/utils/inventario.ts` unifica el precio mostrado (renta/mes vs venta) en ambos selectores.
- **Regla:** La regla #2 (≤ 50 por request) aplica a filas completas para tablas; para **selectores con búsqueda** se puede traer el inventario completo si es la versión ligera (≤ 12 columnas, hoy ~60 KB) — y pedir el registro completo solo al seleccionar. Si el inventario creciera a miles, virtualizar la lista antes que volver a paginar. Verificado que la búsqueda de servidor (`vocal → _` + `ilike`) sí funciona a nivel PostgREST: el problema era el flujo, no la consulta. Limitación: supabase-js solo entrecomilla valores de `.in()` con `, ( )`; si algún día aparecen variantes con espacios al inicio/final, validar que PostgREST las empareje (hoy no existen).
